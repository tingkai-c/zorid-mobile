# Calendar and Reminders bridge

The `ZoridDevice` calendar domain exposes EventKit to deployed React Native app code. The installed binary provides this capability; later interface and orchestration changes can use ordinary direct JavaScript deployment. Calendar and Reminders data stays on the device unless the app explicitly sends it elsewhere. Native permission applies to Zorid as one installed app, so trusted downloaded code shares that grant.

## Permission and native editor

Call `device.calendar.status()` before presenting permission choices. `request({ entity: 'events', access: 'writeOnly' })` requests Calendar creation access; `access: 'full'` also permits reads, updates and deletion. Reminders requires `request({ entity: 'reminders', access: 'full' })`; Apple provides no read-only permission. On iOS 16.4–16.x, the bridge uses the legacy access request, which cannot offer the newer write-only distinction. Denial is reported through the actual native status. See [Apple's EventKit access documentation](https://developer.apple.com/documentation/eventkit/accessing-the-event-store).

On iOS 17+, `editEvent()` can present Apple's editor for a new event without requesting event-store permission. The user chooses what to save in system UI. Editing an existing identifier requires full access. The result is `{ action: 'saved' | 'deleted' | 'canceled', id: string | null }`; a successful editor action does not promise an identifier is exposed to the app. Existing Calendar permission is required on iOS 16.4. Only one editor is active at a time. See [Apple's EventKit UI access sample](https://developer.apple.com/documentation/eventkit/accessing-calendar-using-eventkit-and-eventkitui).

The binary must include `NSCalendarsUsageDescription`, `NSCalendarsWriteOnlyAccessUsageDescription`, `NSCalendarsFullAccessUsageDescription`, `NSRemindersUsageDescription` and `NSRemindersFullAccessUsageDescription`. These strings explain the purpose; they do not grant access. [Apple's migration technote](https://developer.apple.com/documentation/technotes/tn3153-adopting-api-changes-for-eventkit-in-ios-macos-and-watchos) describes the OS-specific requirements.

## Read and write behavior

`calendars('events' | 'reminders')` returns identifiers, titles, colors, modification support and the native default. Write-only Calendar access exposes Apple's virtual/default calendar rather than the person's calendar list. Queries and existing-item mutations require full access, preventing an implicit permission upgrade during a read.

`events({ start, end, calendarIds?, limit? })` takes Unix epoch milliseconds and a positive window of at most 366 days. Returned events are sorted by start time. `limit` is 1–500, default 100; `truncated` reports omitted results. The synchronous native query runs on a background queue with its own event store. `event(id)` returns an event or `null`. EventKit returns all matches before the bridge truncates; this is not cursor pagination. See [Apple's event retrieval documentation](https://developer.apple.com/documentation/eventkit/retrieving-events-and-reminders).

`saveEvent({ event, span? })` creates or updates a nonrecurring event with title, start/end, all-day state, time zone, notes, location, URL, calendar and alarms. Optional omitted fields preserve existing values. `null` clears nullable fields. A supplied alarms array replaces existing alarms; each entry is relative seconds or `{ absoluteAt: epochMilliseconds }`. The bridge permits at most 20 alarms; relative offsets are within 366 days of the start. With write-only access, only new events can be saved, and the response returns `event: null` instead of implying readback access. `removeEvent(id, span?)` removes a nonrecurring event. Native read-only calendars reject mutations. EventKit saves each operation directly; it is not a transaction with Zorid's SQLite records. See [Apple's event creation guidance](https://developer.apple.com/documentation/eventkit/creating-events-and-reminders).

EventKit's identifier lookup can return the first occurrence of a recurring event. The bridge rejects programmatic updates and deletion when the fetched event has recurrence rules; use the native editor to review the event and recurrence choice. It does not expose a recurrence-rule or arbitrary occurrence-targeting codec. Identifiers are device-local and can change after account synchronization. Store them as references that can become unavailable.

## Reminders

`reminders({ calendarIds, completed?, limit? })` requires 1–32 unique Reminders calendar identifiers. It returns scoped results and a `truncated` flag, with the same 1–500 limit. The underlying asynchronous EventKit fetch can read more items before truncation. `reminder(id)` returns one reminder or `null`.

`saveReminder()` supports title, notes, URL, calendar, due/start dates, priority 0–9 and completion. Omitted optional values preserve existing fields; `null` clears dates, notes and URL. `dueDateOnly` and `startDateOnly` preserve calendar-date reminders without adding a midnight time. Supply each flag with its corresponding nonnull timestamp. Native reads report those flags and interpret components without an explicit calendar using Gregorian dates and the device time zone. `setReminderCompleted(id, completed)` changes completion alone; `removeReminder(id)` deletes the selected reminder. These are explicit mutations of the granted native store, including items created outside Zorid. Recurrence rules are not exposed by this first bridge. See [Apple's reminder retrieval APIs](https://developer.apple.com/documentation/eventkit/ekeventstore/fetchreminders(matching:completion:)).

All text fields are bounded to 65,536 UTF-8 bytes and shared device transport is bounded to 8 MiB. Reload cleanup dismisses an owned editor and settles it as canceled, cancels pending reminder fetches, and discards stale event-query replies. It cannot retract an authorization request or undo an already committed EventKit write. Physical-device acceptance remains necessary for permission prompts, system editor behavior, account-backed identifiers and native save results.
