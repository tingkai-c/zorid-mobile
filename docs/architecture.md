# Architecture

Zorid is a native-rendered personal workspace whose JavaScript feature library can evolve without reinstalling its native shell. The first feature slice is tasks → focus session → calendar history. Features share durable identities, rather than keeping unrelated copies of a task in each screen.

The immediate product goal is a growing personal productivity app with reusable native capabilities. Paired-host deployment is an iteration tool; independently delivered app bundles and additional launcher management are deferred.

## Running foundation

Bun manages dependencies, scripts, tests and the desktop/WSL host CLI. Expo SDK 58 and React Native provide the iPhone app, Expo Router the downloaded app’s routing, and Expo SQLite its persistent local records. The native shell has no required tab bar or Settings route. The demo owns Today, Tasks, Focus and Calendar tabs; a new whole-library release can replace its entire interface. There is no independent arbitrary-bundle plugin runtime.

Runtime `zorid-3` shares `group.app.zorid.mobile/SQLite/zorid.db` between the app and native actions. SQLite backup migrates the former app-sandbox database, including WAL records, and retains the original. App mutations read fresh records inside an exclusive write transaction; native handlers transact against the same file. Foreground activation and native record events refresh app state.

`src/storage/documents.ts` stores namespaced documents with stable IDs, a payload schema version, update time and JSON data. `src/features/workspace.tsx` hydrates and validates records before edits and serializes mutations. UI state changes after a successful durable write. Tasks reference UUIDs; focus sessions preserve the task title as a historical snapshot. Timer state is timestamps plus closed work intervals, so pausing does not count as work and restarting the app can restore elapsed time. Reconciliation caps completed work at the target duration when the app resumes; there is no background JavaScript timer guarantee.

All personal records currently live on the device. They remain available offline without a paired host. This does not yet provide cross-device sync, a desktop data client, a production data backend, attachments, a Notion editor or CRDT collaboration.

## Code delivery and trust

The paired host is a code delivery service, separate from personal-data storage. A local Bun CLI publishes whole-library exports. Tailscale Serve supplies HTTPS; a short-lived single-use QR offer pairs a phone. The installed binary pins the host origin, runtime compatibility string and update-signing certificate. The phone keeps its bearer credential in SecureStore. The native shell restores update request headers from the same Keychain record used by Expo SecureStore before checking or fetching releases.

Expo Updates supplies the installed client and compatible protocol; the host supplies manifests and immutable assets without EAS hosting. The initial native setup pairs and downloads the first compatible app; subsequent launches open the cached app directly. Native settings provides check/download/apply controls. Host rollback republishes a prior compatible payload; native crash recovery and authenticated downloads still require physical-device acceptance. Changing native modules, extension configuration or trust anchors requires a signed binary rebuild. See [host operation and limitations](host.md) and [iOS builds](ios-builds.md).

## Native launcher

Runtime `zorid-2` adds the local `modules/zorid-shell` Expo module. UIKit attaches a one-second three-finger hold to the scene window. Core Motion detects a shake while the scene is active. The Home Screen quick action works on cold and warm launches. Each explicit entrance opens Zorid Settings in a tall native bottom sheet and plays one opening haptic, upgraded to heavy at full intensity in runtime `zorid-4`. Swipe down or tap Done to return to a loaded app. During initial setup the sheet stays open until an app loads. The SwiftUI interface and native entrances are compiled into the binary and work independently of downloaded JavaScript. `plugins/with-zorid-shell.cjs` preserves the scene hooks across Expo prebuild.

An embedded launch shows connection setup, rather than the embedded demo. The native coordinator owns initial presentation; the JS root supplies a fallback setup button. Pairing accepts a pasted link or native camera QR scan, validates the binary-pinned host, saves the credential in Keychain, and attempts the first compatible download. Cached OTA launches show the app without requiring network access. Replacing the app’s code does not replace this native settings surface. Runtime `zorid-1` binaries retain their older JS Settings interface and cannot receive the new runtime’s releases.

Offline startup works while the saved pairing remains: Expo restores its persisted request-header override before selecting cached code. Explicitly disconnecting clears that override. Expo SDK 58 includes request headers in cache identity, so the next startup returns to setup until pairing and downloading again; rotating a device token can similarly require another download. Personal SQLite records remain intact. The disconnect UI states this limitation. Preserving cached-code access across credential changes needs a separately validated update-client change, rather than retaining revoked delivery credentials.

Runtime `zorid-4` also exposes UIKit impact, selection and notification feedback to deployed code, with optional impact intensity, view-relative locations on iOS 17.5+, and cached generator preparation/reset. Hardware capability is advisory; iOS controls actual feedback. Older binaries report the bridge unavailable. See [haptics](haptics.md).

Runtime `zorid-5` extends the shell with custom Core Haptics pattern players. Deployed code supplies bounded AHAP JSON for transient/continuous events, parameters and curves; native advanced players own event timing, pause/resume, seek, looping and dynamic controls. The engine is haptics-only: audio events/resources and raw actuator samples are outside this implementation. Foreground loss, interruptions and engine resets can invalidate handles without replay. Availability, accepted commands and projected player state do not measure physical feedback. See [the exact pattern API and budgets](haptics.md#custom-core-haptics-patterns).

## Common device APIs

Runtime `zorid-5` adds `modules/zorid-device` and the optional `src/device` facade for standalone authentication, local notifications and response receipts, clipboard text/URLs, system photo picking and add-only saving, and EventKit Calendar/Reminders access plus Apple's event editor. The versioned capability response describes installed features rather than authorization. JSON requests are snapshotted and bounded, native operations validate their own parameters, and older binaries fail with an explicit upgrade message. Notification actions persist bounded receipts for later consumption; they do not automatically run downloaded code while React is absent. See [device contracts, privacy and limits](device.md).

`src/device/expo.ts` separately re-exports official installed SDK 58 modules for files/document picking and Quick Look, foreground location, contacts, audio, sensors, battery/network/device status, printing/PDFs, camera, SecureStore and other existing APIs. Reuse those interfaces instead of maintaining duplicate Swift wrappers. The separate entry lets compatible code import native dependencies after checking availability; some modules require their native counterpart during import. [Executable opt-in examples](../examples/native-capabilities.ts) cover resource cleanup and permission-sensitive flows; see [official API usage](device-expo.md).

The binary compiles purpose descriptions for the supported user-selected flows. Importing the facades does not itself request permission or start personal-data queries, recording or subscriptions. Ask for the relevant OS grant when a person chooses a feature, preserve limited/denied/restricted outcomes, and remove listeners or stop resources on inactivity/unmount. App namespaces organize data but share one installed app identity, sandbox and OS grants. These capabilities belong to the React Native app process; they are not automatically available in widget rendering or the isolated durable-action SDK.

The official namespaces expose their SDK interfaces, including operations whose background configuration is not enabled here. Background location/audio, remote pushes, general background jobs and additional native services need separately designed lifecycles and any required binary configuration. This is practical common capability coverage, not unrestricted Apple framework access; see the [capability catalog](apple-capabilities.md). A compatible runtime `zorid-5` binary must be installed once before its APIs can evolve through direct JavaScript deployment. Source integration and typechecking do not establish shipping or physical-device acceptance; [delivery evidence](verification.md) records those separately.

## Native surfaces

`src/native/surfaces` isolates focus publication from storage. Expo Widgets renders WidgetKit/ActivityKit layouts from installed supported native components; a failed surface update does not discard local records. Native date-based countdowns continue visually without per-second JS writes. The operating system controls widget refreshes and Live Activity lifetime. New renderers/capabilities need a new binary. Focus Pause, Resume and Finish buttons dispatch versioned JavaScript handlers through native App Intents, independently of the React interface. Shared records, duplicate receipts, outbox entries and surface effects commit atomically. All iOS focus publication, including foreground startup, uses one ordered durable effect path to prevent stale app snapshots overwriting widget actions. Live Activity effects update/end existing activities and can request creation when the app execution context permits it. Ending supplies final content and uses the [system's default dismissal policy](https://developer.apple.com/documentation/activitykit/activityuidismissalpolicy/default), which can retain the final Lock Screen card for up to four hours or until the person dismisses it. Earlier binaries removed it immediately. The completion layout also handles iOS marking a running activity stale at its deadline; this is a system-scheduled rendering change, not a guarantee that background JavaScript runs or that records are finalized at that exact moment. A general visual widget editor remains future work. See [downloaded actions](actions.md).

## Downloaded app entrances

Runtime `zorid-4` adds a device-local Screen Time policy bridge, Device Activity Monitor, Shield Configuration and Shield Action extensions. Deployed code can request a native picker, apply an existing blocklist/allowlist to a focus deadline, and configure all nine public shield appearance fields and native response choices. Newer menus and the open-parental-controls-app response are gated by reported iOS support. The durable action SDK queues restrictions independently of widget updates, so native timer controls can release or restore protection without React running. All five participating targets require compatible Family Controls distribution profiles before TestFlight. This is not full framework coverage: usage reports, website filtering and additional managed restrictions are not implemented. See [Screen Time API, limits and delivery](screen-time.md).

Runtime `zorid-3` supports three dynamic Home Screen quick actions alongside installed Zorid Settings. Downloaded apps register their labels, icons and destinations. Validated `zorid://apps/<appId>/...` links and quick-action destinations persist in a bounded native queue until a matching downloaded route handler succeeds. Handled warm links bypass Expo Router forwarding; cold transport links are rewritten to a valid root until hydration finishes. External URLs do not automatically execute record mutations. See [routes and quick actions](routes.md).

## Future shared data backend

[The PostgreSQL schema](../backend/README.md) is an independently testable foundation, not a connected service. Collections and property definitions describe user-created databases; records contain JSONB payloads and payload versions; relation edges carry database-enforced same-workspace references. A normalized focus timeline supports calendar queries. The database uses tombstones to leave room for later deletion propagation.

JSONB permits adding fields without immediately altering a SQL table and supports indexing, but does not remove semantic migrations or validation. See [PostgreSQL JSON documentation](https://www.postgresql.org/docs/18/datatype-json.html). Database constraints enforce structural invariants, with application validation still needed for user-defined property semantics; see [PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html).

PowerSync is a candidate for PostgreSQL-to-local-SQLite synchronization. Yjs is a candidate for convergent rich-text documents. Neither is integrated or validated here. A two-client proof must establish offline writes, access control, tombstone propagation, conflict handling, migrations, reconnect and backup recovery before selecting and deploying the sync layer. Realtime transport alone does not define merge semantics or durable synchronization.

Expected conflicts need explicit product rules. Simultaneous task edits can use expected revisions and deliberate field merges. Two devices starting focus offline must reconcile competing sessions. Rich text may use CRDT operations; a CRDT should not silently decide task completion, timer ownership or relational integrity. Attachments belong in a separate blob store referenced by records, with quotas and authorization.

Local document formats and the server schema are currently different representations. There is no implicit migration or upload. A future adapter must map identity, timestamps, JSON properties and interval formats and define ownership/authentication before exposing data. Schema versions, additive migrations, old-client compatibility and rollback-readable data remain necessary even with JSON and CRDTs.

## Execution and validation

WSL performs development, dependencies, tests and JavaScript export. GitHub macOS runners generate native projects, compile/sign and upload build artifacts; the Mac only installs the signed app. Tests cover pure focus transitions, local document SQL, host protocol and native snapshot logic. Native compilation is separate evidence from successful installation, offline launch, pairing, OTA recovery and real widget rendering on a registered iPhone.
